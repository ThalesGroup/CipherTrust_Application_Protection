Building Secure RAG with Snowflake Cortex Search and Thales CRDP

A technical pattern for protecting PII before it enters retrieval context.

Architecture, controls, and implementation guidance

Retrieval Augmented Generation (RAG) lets an LLM answer from enterprise knowledge rather than from general training data alone. A user question retrieves relevant document passages, which are supplied to the LLM as grounded context. Internal documents can contain personal information, compensation data, contact information, and confidential business facts.

This defense-in-depth pattern uses Snowflake Cortex Search, Snowflake document processing, Snowpark Container Services, and Thales CipherTrust REST Data Protection (CRDP). Its central control is simple: protect sensitive values before the document becomes searchable RAG context, then reveal values only through a separately authorized path.

  1. Parse staged documents in Snowflake.
  2. Identify candidate sensitive entities.
  3. Protect values through Thales CRDP.
  4. Persist and index only sanitized text.
  5. Return protected answers by default and reveal only when policy permits.

Architecture and trust boundaries

  • Snowflake internal stage and parsing. An internal stage with directory metadata holds documents; PARSE_DOCUMENT extracts text inside Snowflake.
  • Sensitive-data identification. A Cortex LLM extraction prompt, deterministic detector, or both produces candidate entities. Validate LLM output before it drives an irreversible transformation.
  • Thales protection service. A Snowpark Container Services endpoint calls CRDP bulk protection and reveal policies. The container does not contain data-protection keys.
  • Sanitized RAG corpus. The Cortex Search source contains document metadata and sanitized text, not a convenience RAW_TEXT column.

Snowflake roles control access to stages, tables, search services, and functions. Thales adds policy enforcement around the data values, including which caller or use case may request a reveal. These controls complement rather than replace one another.

1. Stage documents and extract text

An internal stage and directory metadata let the pipeline enumerate documents without a manually maintained file list.

CREATE OR REPLACE STAGE DOCS
  ENCRYPTION = (TYPE = 'SNOWFLAKE_SSE')
  DIRECTORY = (ENABLE = TRUE);

ALTER STAGE DOCS REFRESH;

CREATE OR REPLACE TEMPORARY TABLE TEMP_PARSED_CHUNKS AS
SELECT RELATIVE_PATH AS FILE_NAME,
  SNOWFLAKE.CORTEX.PARSE_DOCUMENT('@DOCS', RELATIVE_PATH, {'mode': 'LAYOUT'}):content::STRING AS RAW_TEXT
FROM DIRECTORY('@DOCS');

The temporary table is a processing boundary, not the future RAG source. Apply least privilege to the stage and do not copy extracted cleartext to permanent diagnostics, query exports, or application logs. Define ingestion error handling, document-size limits, supported file types, and retention for source files.

2. Detect and validate sensitive entities

The proof of concept uses SNOWFLAKE.CORTEX.COMPLETE to return a JSON list of PII candidates. A prompt can request an extracted value and routing class, such as char for names, emails, and formatted phone numbers, or number for numeric values.

SELECT SNOWFLAKE.CORTEX.COMPLETE('mistral-large2',
  CONCAT('Extract PII from this text. Return JSON with entity_value and ',
         'detected_type. Use number only for pure numeric values. Text: ', RAW_TEXT),
  {'response_format': {'type': 'json_object'}})
AS EXTRACTED_JSON FROM TEMP_PARSED_CHUNKS;

Treat this as candidate metadata. Validate JSON shape, cap entity count and length, normalize duplicates, and verify each entity occurs in source text. For high-risk data types, combine LLM extraction with deterministic patterns, business dictionaries, or human approval. If an entity cannot be classified or protected, fail closed and move the document to a restricted exception queue.

3. Protect values using Thales CRDP

The Snowflake application does not perform encryption itself. It sends batches to CRDP through Snowpark Container Services, and CRDP applies the configured policy. This centralizes algorithm, key, and policy decisions while supporting separation of duties between Snowflake administrators and security teams.

The demonstration uses separate character and numeric protection functions. It prefixes each returned token with application-level routing metadata, so an authorized reveal function can choose the matching CRDP policy. The prototype's base64-encoded char# and nbr# headers are not cryptographic protection; they can disclose a broad value class. Use an opaque format if that classification is sensitive, and avoid logging full tokens.

Y2hhciM=$<protected-character-value>
bmJyIw==$<protected-numeric-value>

Use TLS for CRDP service-to-service calls, with server verification and client certificates where required. Keep CA certificates, PKCS12 files, and passwords in Snowflake secrets or a cloud secrets manager, never in a Dockerfile, committed service specification, application defaults, or query history.

4. Build the sanitized corpus, then create Cortex Search

After protection, reconstruct each document by replacing raw entities with protected values. Persist sanitized text and non-sensitive metadata, then drop temporary cleartext tables.

CREATE OR REPLACE TABLE PROCESSED_DOCUMENTS_RAG AS
SELECT FILE_NAME, SANITIZED_TEXT, CURRENT_TIMESTAMP() AS INDEXED_AT,
  'v1' AS PROTECTION_PIPELINE_VERSION
FROM TEMP_SANITIZED_DOCUMENTS;

CREATE OR REPLACE CORTEX SEARCH SERVICE RAG_SEARCH
  ON SANITIZED_TEXT ATTRIBUTES FILE_NAME WAREHOUSE = RAG_WH TARGET_LAG = '1 hour'
AS SELECT FILE_NAME, SANITIZED_TEXT FROM PROCESSED_DOCUMENTS_RAG;

Manual embeddings with EMBED_TEXT_768 and vector similarity are useful for a proof of concept. For a Cortex Search production pattern, use the sanitized table as the service source instead of maintaining an application-managed vector column. The important security property is that the source is sanitized before indexing.

5. Generate a protected answer by default

At query time, search sanitized content, build a bounded context window, and instruct the LLM to use only that context. The prompt should direct the model to preserve protected tokens exactly and not infer or fabricate values. The protection comes from the sanitized prompt context, not the instruction alone.

Use only the supplied context. Preserve protected tokens exactly as written.
Do not infer their values. If the answer is unavailable in the context, say so.

Set maximum result counts and context sizes, record correlation IDs, and avoid storing full prompts or answers in broadly accessible logs.

6. Reveal only through an authorized path

The prototype's REVEAL_TAGGED_TEXT function scans a protected answer, reads routing metadata, and calls the matching Thales reveal function. Do not make it universally executable. Place it behind a dedicated Snowflake role and expose it through a controlled view, stored procedure, or application API. Log every reveal decision.

Evaluate more than a user name: include invoking role, application identity, data domain, request purpose, and time-bound approval. Align the Thales policy to the same model. If reveal fails, preserve the protected value rather than leaking context in an error or substituting a guessed value.

Same question, two governed outcomes

The following fictional example shows the desired default behavior. The RAG answer remains useful to any permitted user, but only an authorized role may invoke the reveal path to obtain cleartext values.

Protected response (any permitted role)

  • Sarah Conner: total compensation package mapped to bmJyIw==$71425 USD
  • Michael Scott: current salary established at bmJyIw==$10015 USD

Revealed response (authorized roles only)

  • Sarah Conner: total compensation package mapped to 92000 USD
  • Michael Scott: current salary established at 88000 USD

Operational controls for production

  • TLS and secrets: use mTLS where required, verify certificates, rotate credentials, and never disable verification outside controlled testing.
  • Idempotency: store a document hash and pipeline version to avoid repeatedly protecting already protected content during retries.
  • Least privilege: grant only required access to stages, source tables, Cortex Search, protection functions, and reveal functions.
  • Observability: capture document ID, version, entity counts, logical policy route, status, and correlation ID, while keeping raw text and full tokens out of logs.
  • Quality: test extraction recall and precision, replacement correctness, retrieval relevance, answer faithfulness, and reveal authorization with representative documents.
  • Retention: define when source files, temporary parsed text, sanitized documents, and audit records are purged.

A reusable security pattern for enterprise AI

Sensitive values are protected before documents become a retrieval corpus, so the default AI path works with information that remains useful but is less exposed. Snowflake Cortex Search provides managed retrieval, Snowpark Container Services hosts the CRDP integration close to Snowflake workloads, and Thales controls the protection and reveal policy around the values that require the most care.
