Thales + Snowflake | Technical Solution Overview

Thales CipherTrust RESTful Data Protection on Snowpark Container Services

A Snowflake-native deployment pattern for SQL-accessible encryption and tokenization, with centralized Thales policy and key management.

Solution intent

Run the Spring Boot service integration as a private Snowflake service. SQL service functions invoke its protect or reveal endpoints; the integration communicates with CRDP; CRDP enforces protection policy and uses CipherTrust Manager for key management.

This pattern keeps the custom integration layer within Snowflake while retaining a dedicated Thales control plane for cryptographic policy and keys.

Logical request path

1. Snowflake SQLUDF, procedure, or view calls a service function with a batch of values.
2. SPCS UDF serviceSpring Boot validates the Snowflake request envelope and routes protect/reveal work.
3. Thales CRDPCRDP applies the selected encryption or tokenization policy through its REST API.
4. CipherTrust ManagerCentralized key management and policy control support CRDP operations.
Core services

Two private SPCS services

  • UDF service: Java/Spring Boot REST adapter exposed to Snowflake service functions.
  • CRDP service: Thales CRDP container, normally exposed privately on its internal service endpoint.
  • Service-to-service path: UDF service calls the CRDP internal DNS name and port.
Control plane

Snowflake and Thales responsibilities

  • Snowflake manages image repositories, compute pools, service lifecycle, role grants, event telemetry, and permitted egress.
  • Thales CRDP and CipherTrust Manager own protection policies and key-management interactions.
  • Platform teams own deployment configuration, certificates, secret rotation, monitoring, and capacity decisions.

Architecture choice

External functions and SPCS: different operating models

External Functions are appropriate for many integrations. SPCS becomes compelling when the custom service is data-intensive, needs a managed container runtime, or should operate within Snowflake's service, governance, and observability model.

DimensionExternal FunctionThales CRDP on SPCS
ArchitectureSnowflake invokes a remote endpoint through an API integration.Snowflake runs the application integration as a containerized service on a compute pool.
Data pathInput values leave Snowflake for the remote endpoint and results return.The UDF integration runs within Snowflake, so the integration layer does not require an application-controlled external endpoint. CRDP-to-CipherTrust Manager connectivity is separately governed.
Runtime ownershipTeam operates capacity, patching, telemetry, and network security for its cloud service.Team packages the image and declares the service; Snowflake manages the underlying container-service infrastructure and compute pool.
ScalingRemote platform capacity and concurrency are separately designed and operated.Compute-pool node ranges and service instance ranges are defined in Snowflake. Scale behavior must be tuned and validated for the workload.

Design rule: Do not treat SPCS as a claim of "zero network traffic." It reduces the need to send values to an independently hosted integration endpoint, but a CRDP deployment may still require an approved outbound connection to CipherTrust Manager. Model each hop explicitly.

SPCS objects in this solution

Image repository and compute pool

The UDF and CRDP images are uploaded to a Snowflake image repository. Services run on a compute pool whose machine type and node range are selected for availability and throughput needs.

Long-running services and endpoints

Each container is deployed with CREATE SERVICE. The UDF endpoint is used by Snowflake service functions. The CRDP endpoint is private and reached by internal service DNS; the endpoint protocol is TCP even when the application protocol on that port is TLS.

Security and deployment

Private connectivity, TLS, and controlled configuration

Transport security modes

The UDF service can call CRDP without TLS for tightly controlled proof-of-concept deployments, or with TLS for production-oriented deployments. The selected CRDP server mode and the Java client configuration must agree.

CRDP modeUDF service requirementTypical use
no-tlsCRDP_SSL_ENABLED=falseNon-production validation only when approved by the organization's security policy.
tls-cert-optEnable TLS and provide the CA certificate used to validate the CRDP server.Server-authenticated TLS between the UDF and CRDP service.
tls-certEnable TLS, provide CA trust, and provide a PKCS#12 client certificate and password.Mutual TLS where CRDP authenticates the client service.
Secrets

Keep sensitive material out of images

  • Use Snowflake secrets for registration tokens, certificate/key PEM values, PKCS#12 content, and passwords.
  • Mount trust material as a secret file when the Java client expects a file path.
  • Use stage volumes only for non-sensitive deployment artifacts or a trust-only CA bundle governed with the appropriate stage controls.
  • Never place private keys or credential values in the Dockerfile or service-spec env block.
Network

Separate inbound and outbound controls

  • Keep UDF and CRDP endpoints private unless an external endpoint is explicitly required.
  • Use internal service DNS for UDF-to-CRDP communication.
  • Allow CRDP's outbound connection to CipherTrust Manager through a narrowly scoped external access integration.
  • Validate server certificate SAN against the CRDP internal DNS name used by the UDF client.

Illustrative service boundary

Snowflake SQL service function
  -> private UDF endpoint (HTTP)
  -> UDF uses https://<crdp-service>.<dns-domain>:8090
  -> private CRDP TCP endpoint, with TLS handled by CRDP
  -> approved external access path to CipherTrust Manager
Operational recommendation: Load certificates and trust material once at service startup. Rotate secrets through a controlled redeployment and validate readiness, CRDP registration, TLS handshake, and a protect/reveal smoke test before releasing the prior service revision.

Operating the solution

From SQL call to reliable production service

Application contract

Snowflake sends service-function requests to the Spring Boot adapter in batches. The adapter preserves the row ordering required by the Snowflake response envelope, applies the selected CRDP policy and metadata behavior, and returns the protected or revealed values. Existing applications can continue to call the established SQL functions while the container implementation evolves behind the endpoint.

Performance design

  • Batch values to reduce per-request overhead; tune batch size against CRDP latency, payload size, and service-function limits.
  • Size UDF and CRDP instances independently. A slow CRDP policy operation should not be hidden by simply increasing Snowflake warehouse size.
  • Measure p50/p95 latency, error rate, CRDP connection reuse, instance saturation, and end-to-end rows per second.
  • Test realistic policy types and data distributions, not only a small happy-path sample.

Reliability design

  • Use readiness probes and private endpoints for both services.
  • Set timeouts deliberately and distinguish retryable transport failures from protection-policy errors.
  • Emit structured logs without plaintext values, keys, passwords, tokens, or certificate bodies.
  • Use Snowflake event tables and service status information with CRDP/CipherTrust operational telemetry for incident triage.

Implementation and governance checklist

AreaProduction decision
Identity and accessDefine distinct Snowflake roles for image deployment, service operation, SQL function use, secret administration, and CipherTrust policy administration.
Key and policy modelDefine which Thales policy protects each logical field, which users may reveal data, and the evidence required for change control.
CertificatesUse a CA trust bundle for server validation; use PKCS#12 client identity only for mutual TLS; automate expiry monitoring and rotation.
Data discoveryUse Snowflake classification and Cortex-oriented data workflows to prioritize sensitive fields, then apply approved Thales protection policies.
Cost and scaleChoose compute-pool sizes and service minimum/maximum instances from measured workload concurrency, not a generic default. Review utilization and idle time regularly.

Recommended rollout

Begin with a non-production environment and one sensitive column category. Deploy server-authenticated TLS first, prove correct protect/reveal behavior and authorization, then add mutual TLS if required. Promote the same container image and declarative service specifications through environments, with environment-specific secrets, network integration, and policy identifiers supplied at deployment time.
